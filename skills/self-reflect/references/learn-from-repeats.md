# Learn from repeated mistakes

Use after a recurring mistake, or a single failure at a consequential safety
boundary, to decide whether the working method needs repair. Fix the current
task within its authorization first. A correction does not automatically
authorize changing global instructions, checks or unrelated repositories.

## Find the failed decision

Name the behavior and inspect the relevant source, tool results and earlier
occurrences. Use existing issues, reviews and task records; do not create a
lesson ledger. Distinguish two separate occurrences from retries of one failure.
Respect a recorded rejection unless new evidence changes its premise.

Locate the first wrong decision. An ignored rule may reflect missing context,
an ambiguous trigger, a tool defect, a conflicting instruction or inadequate
enforcement. Diagnose that cause before adding a stronger rule. One ordinary
mistake usually needs a local correction, not a permanent workflow.

## Choose the smallest durable repair

Put project facts with their owner and reusable working methods in Skills.
Prefer the lowest layer that can prevent the failure:

1. An existing owner or interface that makes the wrong path unnecessary.
2. A type, schema, permission, lint rule or runtime check that rejects it.
3. A regression test that exposes the mistake.
4. One concise instruction when the decision requires judgment.

A hook is useful only where the runtime invokes it and its check can establish
the required fact. Another sentence is useful only if it changes a decision.
Do not build a service, ledger or general policy engine for a local correction.

For a proposed repair, retain the failure evidence, affected owner, exact change,
verification and recurring cost in the existing task record or PR. Use the
[documentation boundary](../../follow-instructions/SKILL.md#documentation-boundary)
for working notes. Keep source attribution in the catalog, not in agent steps.

## Apply and verify

Reuse explicit authorization for the affected workflow. If it is outside the
approved scope or requires a new permission, prepare the concrete change and
ask for that decision while continuing independent work. Follow
[plans and authority](../../follow-instructions/references/approved-plans.md).
Reflection alone supplies no additional permission.

Exercise the original failure and a different valid result. When changing an
evaluator, preserve independent acceptance, test meaningful defects and valid
alternatives, and report revised measurements separately. Never loosen a check,
threshold or permission to make the implementing agent's result pass.

For skill changes, use [skill-creator](../../skill-creator/SKILL.md). A targeted
regression can establish that a defect was repaired; a claim of better agent
performance also needs the baseline comparison defined there.

Remove a superseded instruction when the repair makes it unnecessary. Keep an
exception with the boundary it affects and explain its reason. Reconsider it
when that reason or boundary changes rather than creating arbitrary expiry
dates. Do not apply a rejected proposal or rewrite unrelated user guidance.
